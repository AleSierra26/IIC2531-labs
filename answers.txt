3. http.c:
    void url_decode(char *dst, const char *src)
    {
    for (;;)
    {
        if (src[0] == '%' && src[1] && src[2])
        {
            char hexbuf[3];
            hexbuf[0] = src[1];
            hexbuf[1] = src[2];
            hexbuf[2] = '\0';

            *dst = strtol(&hexbuf[0], 0, 16);
            src += 3;
        }
        else if (src[0] == '+')
        {
            *dst = ' ';
            src++;
        }

        {

            src++;

        }

        dst++;
    }

Podemos ver que process_client reserva un espacio en el buffer con reqpath[4096].

Por otra partd http_request_line leee la primera linea de HTTP en buf[8192] y luego pasa el path (sp1)
a url_decode, para que lo copie en reqpath. El problema es que, no hay verificación de longitud en
url_decode. 

Si el path supera 4096 bytes, url_decode escribe en el buffer mas alla de reqpath,
vulnerando el frame de process_client y la direccion de retorno.

Ademas, url_decode permite ingresar bytes de la forma %xx (como \x00 con %00 y no se detiene el
bucle en ese caso), lo que facilita la escritura de codigo malicioso en la pila

Para generar una solicitud HTTP maliciosa, necesitamos que el path sea mayor a 4096 bytes, 
y que con ese texto se alcance, y sobrescriba, la direccion de retorno de process_client.

Un ejemplo podria ser:

GET /AAAAAAAAA...."codigo malicioso"...AAAAAAAA... HTTP/1.0
Host: x

En donde despues de "/" ponemos un contenido mayor de 4096 bytes, de esta forma se escribira mas
alla de reqpath en la pila (direccion de retorno y otras variables), generando un buffer overflow.

Adicionalmente, si queremos generar mas daño, en nuestro "relleno" podemos ingresar algun tipo de
codigo malicioso que infecte el programa. Por ejemplo, sobreescribir en la direccion de retorno, 
para que apunte a algun sitio donde hayamos puesto codigo malicioso.


Parte 4:
1. Otra vulnerabilidad que pude encontrar es la nula verificacion del path en la request.
    A lo que me refiero es que, en http_request_line, no se verifica si el path tiene algun
    tipo de secuencia especial, como "../" o "/./", que permitan salir del directorio raiz
    (root_dir) y acceder a archivos fuera de este. En particular, se podria acceder a
    archivos sensibles del sistema, como /etc/passwd, si el servidor tiene los permisos
    necesarios. 
    Paso 1: El usuario manda una request con un path que contenga "../" para salir
    del directorio raiz. GET /../../../../etc/passwd HTTP/1.0
    Paso 2: El servidor procesa la request y concatena el path con root_dir.
    http_request_line:
    url_decode(reqpath, sp1);
    envp += sprintf(envp, "REQUEST_URI=%s", reqpath) + 1; 

    process_client:
    http_serve(fd, getenv("REQUEST_URI"));

    http_serve:
    getcwd(pn, sizeof(pn));
    strncat(pn, name, sizeof(pn) - strlen(pn) - 1);
    
    Paso 3: El servidor accede al archivo fuera de root_dir, en este caso /etc/passwd, y se lo 
    envia al cliente con http_serve_file().

    Con esto el atacante puede leer archivos sensibles del sistema, como /etc/passwd, archivos
    de configuracion, logs, etc, robar codigo fuente y ejecutar scrripts maliciosos.
    Como limitaciones tenemos que solo puede acceder a archivos que el usuario del proceso
    del servidor tenga permiso de leer, y si el servidor en un contenedor, el daño se limita a 
    ese entorno.
    La vulnerabilidad funciona porque concatenar cadenas no tiene en cuenta secuencias de escape
    como ../, rutas absolutas, o links dentro del sistema que apunten fuera del root.
    Esto se puede solucionar normalizando la ruta con realpath() y verificando que la ruta
    resultante este dentro de root_dir o rechazando secuencias peligrosas en el path. Si el
    path contiene .., //, o empieza con /, responder con 403 Forbidden.

2. Otra vulnerabilidad que pude encontrar es el bloqueo del sistema (DoS). En run_server() el 
    proceso padre hace accept(), fork() y luego hace wait(&status) y bloquea hasta que ese hijo 
    termine. Eso significa que el padre deja de aceptar nuevas conexiones mientras espera a que el 
    child termine, lo que genera quen un usuari malicioso puede dejar al child esperando, 
    provocando que el servidor deje de atender nuevas conexiones.
    Podemos ver que:
    static int run_server(const char *port)
    {
    ...
    int cltfd = accept(sockfd, NULL, NULL);
    ...
    switch ((pid = fork())) {
    ...
    case 0:
        process_client(cltfd);
        exit(0);
    default:
        close(cltfd);
        pid = wait(&status);
    ...
    }
    El problema con esto es que cuando el padre hace hace wait() se bloquea hasta ese hijo termine.
    Si el hijo está bloqueado esperando datos, entonces el padre permanece bloqueado también.
    Mientras el padre esté bloqueado, no se vuelve a llamar accept(), es decir, las nuevas 
    conexiones fallan o esperan.
    Para explotar esta vulnerabilidad, un atacante puede abrir una conexión al servidor y no
    enviar datos, dejando al child esperando. Esto bloquea al padre en wait(), impidiendo
    que atienda nuevas conexiones, causando una denegación de servicio (DoS).
    El atacante puede lograr una caida parcial o total del servicio, dependiendo de la cantidad
    de conexiones que abra y deje esperando.
    La unica limitacion del atacante es la cantidad de conexiones que el sistema permita abrir, y
    la capacidad misma de abrir conexiones con el servidor.
    Esto funciona porque wait() es bloqueante, es decir, espera hasta que un hijo termine antes de
    seguir aceptando a otros (o ejecutar cualquier cosa en realidad).
    Una solucion simple es usar un manejo de señales para los hijos terminados. Es decir, en vez
    de usar wait() bloqueante, los hijos mandaran una señal cuando terminen, y el padre puede
    manejar esa señal para limpiar los procesos hijos terminados, de esta forma el padre no se 
    bloquea y puede seguir aceptando nuevas conexiones, mientras sus hijos realizan sus procesos.
